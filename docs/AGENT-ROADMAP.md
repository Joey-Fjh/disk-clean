## 阶段 1：合并扫描与空间分析

### 目标

将「安全清理（规则扫描）」与「空间分析」合并为**单一扫描入口**的前置空间发现流程；移除或隐藏用户层面的双模式切换。

### 包含范围

- 统一「开始扫描」流程：先磁盘/目录占用概况，再进入后续分析管线。
- `ScanEngine` 层整合 `RuleScanner` 与 `DiskAnalyzer` 的触发顺序（可并行或分步，由设计定）。
- UI：去掉模式选择器或改为内部策略，用户只见一条主路径。
- 保留取消扫描、增量推送结果的能力。

### 不包含范围

- Agent / LLM 调用。
- 结果分档语义变更（仍可用现有三档 Tab）。
- API Key 设置页。
- JSON 规则降级重构。

### 主要修改区域

- `src/main/scanner/scan-engine.ts`、`disk-analyzer.ts`、`rule-scanner.ts`
- `src/renderer/index.html`、`main.ts`
- `src/shared/types.ts`（`ScanMode` 等可能调整）
- 相关集成测试

### 测试要求

- 选定单盘 / 全盘扫描均能得到空间概况 + 规则项（或占位后续 Agent 的目录摘要）。
- 取消扫描不崩溃，已发现项保留。
- 现有 `vitest` 套件通过；新增合并流程集成测试。

### UI 验收要求

- 清理页仅一条「开始扫描」主路径（或等价单一 CTA）。
- 扫描中可见空间发现进度，无「选模式」困惑。
- 1920×1080 / 1366×768 布局正常，单滚动区原则不变。

### 完成标准

- 代码中用户路径不再依赖 `quick` / `full` 二选一（或 `full` 仅作内部阶段名）。
- README「当前功能」与实现一致。

### 进入阶段 2 的条件

- 阶段 1 合并扫描稳定，无回退双模式的需求。
- 目录摘要数据结构初稿确认（供阶段 2 Candidate 统一）。

## 阶段 2：统一 Candidate 和结果流程

### 目标

空间占用项、规则扫描项、Agent 建议项统一为 **Candidate（ScanItem）** 模型与展示管线；并定义目标方案所需的**清理资格信息模型**（承载字段，本阶段不修改 Validator 授权逻辑）。

### 包含范围

- 扩展 `ScanItem`（或等价类型），至少承载以下目标字段或等价概念：

| 字段 / 概念 | 用途 |
|-------------|------|
| 判断来源 | 规则扫描 / 空间发现 / Agent 建议 / 本地特征提示 |
| 判断依据 | 可展示的依据摘要（含引用的本地证据） |
| 把握程度 | 高 / 中 / 低或等价表达 |
| 建议结果 | 建议清理 / 需要确认 / 无法确定（或空间占用仅展示） |
| 是否允许用户选择 | 「无法确定」等为 `false`（已确认） |
| 建议的受限清理动作 | 如移入回收站；须为白名单动作 |
| 当前扫描会话与快照信息 | 会话 ID、路径与大小等与快照绑定的校验字段 |

- 统一 Renderer 列表组件与分组逻辑。
- 规则扫描结果、空间发现结果作为 Candidate 的**来源之一**；Agent 建议为另一来源。
- 迁移期：现有三档 Tab 可保留，内部映射到新语义。

### 不包含范围

- 实际调用 LLM。
- API Key 存储。
- 用户经验库写入 UI。
- **SafetyValidator 授权逻辑修改**（留待阶段 6）。
### 主要修改区域

- `src/shared/types.ts`
- `src/main/scanner/rule-matcher.ts`、扫描结果组装
- `src/renderer/main.ts`、`safe-render.ts`
- `tests/` 中与 ScanItem 相关的测试

### 测试要求

- 类型与序列化测试；渲染测试（含 XSS 安全现有用例）。
- 混合来源（规则 + 空间目录）同屏展示无重复 ID 冲突。

### UI 验收要求

- 每项展示：路径（可脱敏）、大小、来源标签、原因/影响（若有）。
- 折叠分组、全选、清理选中行为与现网一致或明确迁移说明。

### 完成标准

- 单一 Candidate 管道可承载阶段 4、5 的 Agent 输出。
- **清理资格信息模型**字段冻结一版，供阶段 6 Validator 迁移直接消费。

### 迁移期说明（重要）

阶段 2 完成**不等于**目标产品已落地。当前仍存在的**双轨行为**是迁移桥，不是终态：

| 当前行为（迁移期） | 目标行为（阶段 4+6） |
|-------------------|---------------------|
| `RuleScanner` 独立产出可清理列表 | 扫盘产生 pending Candidate，Agent 写 judgment |
| JSON 规则命中 → `suggested` / 可勾选 | 规则降为**证据层**，Agent 为主要判断者 |
| `SafetyValidator` 须匹配 JSON 规则 | 会话 Candidate + 用户确认授权（阶段 6） |
| 空间发现 → `pending` 不可勾选 | 同上；Agent 填充 judgment 后可建议清理 |

**阶段 2 验收**确认的是：数据模型、UI 语义、证据展示、执行快照与空间观察分离已就绪；**不是**确认 Agent 已替代规则判断。

### 进入阶段 3 的条件

- Candidate / 清理资格字段冻结一版（可小改，不推翻）。
- 产品确认三档文案与内部 ID 映射表。
- 阶段 2 人工验收通过（含截图）。

## 阶段 3：模型 Provider 与安全凭证

### 目标

实现用户自备 API Key 的配置、加密存储、连接测试；主进程封装模型调用，Renderer 不接触 Key 明文。

### 包含范围

- 设置页：服务商预设、自定义地址、Key、模型名、协议、测试按钮。
- 主进程：Key 加密存取（Windows 系统能力）、连接测试、最小 Chat 调用。
- 脱敏与日志策略：Key 不进日志/导出。
- 参考 CC-Switch 的预设与协议兼容思路，**不**依赖其运行时。

### 不包含范围

- 扫描流程中的自动 Agent 分析（阶段 4）。
- 多 Key 轮换、OAuth、外部 Codex 接入。
- 将模型建议写入清理执行。

### 主要修改区域

- `src/main/` 新增 provider 模块（命名待定）
- `src/preload/` IPC
- `src/renderer/` 设置 UI
- 安全相关单元测试

### 测试要求

- Key 存取模拟测试；Renderer 无法读取明文（IPC 契约测试）。
- 连接失败 / 超时错误信息不泄露 Key。
- 无 Key 时应用其余功能正常。

### UI 验收要求

- 保存后仅显示 Key 末四位；可替换、删除，不可查看完整 Key。
- 连接测试与模型能力测试有明确成功/失败反馈。

### 完成标准

- 在配置有效 Key 的前提下，主进程可完成一次最小模型请求（如 ping 消息）。

### 进入阶段 4 的条件

- 安全评审通过 Key 存储方案。
- 选定第一版支持的协议与预设服务商列表。

## 阶段 4.1：规则体系分层与扫描后规则草稿闭环

### 目标

> **实现状态（2026-08-26）**：**已完成**。详见 [PHASE-4.1-REPORT.md](./PHASE-4.1-REPORT.md)、[RULES-v2.md](./RULES-v2.md)。

### 包含范围

- 四层规则加载与 `config/` 目录迁移（保留旧路径兼容）。
- `RuleDraft v1` 严格 Schema；`agent:generate-rule-draft` IPC。
- 匹配预览、批准编译、设置页「规则与知识库」三 Tab UI。
- 导出规则编写包；导入 JSON 仅进草稿区。
- 旧 `user-rules.json` 幂等迁移。
- **判断矩阵**：本地规则授权清理；Agent 仅复核/降级；`JudgmentOrigin` 来源标签。

## 阶段 6：清理计划与执行闭环

> **实现状态（2026-08-28）**：**已完成**。代码与安全复审通过，无 P0/P1 阻断项。详见 [PHASE-6-REPORT.md](./PHASE-6-REPORT.md)。

### 目标

将 Agent 建议与用户勾选接入 **CleanupPlan → SafetyValidator → Cleaner**；完成 Validator 从规则授权到**会话候选项授权**的迁移；清理后重新扫描并对比结果。

### 包含范围

- **Validator 授权模型迁移（本阶段核心）**：
  - 从「必须匹配 JSON 规则」迁移为「**当前会话候选项 + 用户确认 + 本地安全策略 + 白名单动作**」。
  - 授权须验证：有效会话、候选项 ID（非模型任意路径）、快照一致、`protectedPaths`、路径边界、白名单动作、Agent 已建议、用户确认。
  - **拒绝**：无法确定、未确认、快照变化、受保护路径、模型提供的任意路径。
  - 规则匹配仍可作为**证据与额外约束**，但不再是 Agent 候选项进入 Plan 的**唯一**凭证。
- **兼容迁移**：保留规则驱动旧候选项的迁移路径与测试（现有 `quick` 扫描产出的规则项仍可按规则授权执行，直至完全切换）。
- 执行后自动触发重新扫描或受影响路径复核（具体策略见 PRODUCT §开发阶段待定参数）。
- UI：确认对话框展示 Agent 依据摘要；执行结果与重新扫描对比。
- 过程可视化链路闭环（设计文档 §12）。

### 不包含范围

- 用户经验库（阶段 7）。
- 全量性能优化。

### 主要修改区域

- `src/main/cleanup/plan-builder.ts`、`safety-validator.ts`
- `src/renderer/confirm-dialog.ts`、清理页状态
- 清理集成测试扩展

### 测试要求

- 现有 `cleanup-integration`、`safety-validator` 测试通过并扩展。
- **无 JSON 规则的 Agent 候选项**：在用户确认且会话一致时可执行；任意模型路径、快照变化、protectedPaths 必须拒绝。
- **规则驱动旧候选项**：兼容迁移测试覆盖。
- 重新扫描 / 复核后结果一致性（mock 环境）。

### UI 验收要求

- 二次确认必须展示项数、估算空间、分档摘要与主要依据。
- 清理完成后状态栏/结果区展示实际移入回收站情况。
- 「无法确定」项不可勾选。

### 完成标准

- 端到端：扫描 → Agent 建议 → 用户确认 → Validator（会话授权）→ 回收站 → 重新扫描/复核。
- 无 JSON 规则项可在满足会话授权条件下进入 Plan（目标方案落地）。

- ✅ Validator 迁移评审通过

## 跨阶段原则

1. **每阶段一个主题**，评审通过再前进。
2. **安全底线**自阶段 1 起不得倒退；阶段 3 起 Key 安全；阶段 5 起工具边界。
3. **文档随阶段更新** README「当前功能」与 DECISIONS，避免文档领先实现或实现领先文档。
4. **阶段 2 定义清理资格数据模型，阶段 6 消费并实现 Validator 迁移**——授权设计不得在阶段 6 临时拍板。
5. 当前规则驱动功能在迁移完成前**保持可用**，避免长时间不可用主干。
